# v7.0.4 远程 libc 识别：双符号 low12 指纹 → 自动匹配 libc → ret2libc 全自动

- **索引位置**：`upgraded.md §2`
- **状态**：✅
- **Owner**：@Minzhi_Zhou
- **预估 / 实际**：4h / 3.5h

## 1. 背景

v7.0.3 的 `canary_echo` 在 repeater 远程实例（`*.tcp-ctf2.dasctf.com`，TLS）上失败，
2026-11-14 手工复盘：本地容器 glibc 2.35（puts low12=0xe10），远程泄漏 low12=0x6a0
→ `_find_libc_base` 永不匹配 → 40 个 ret2libc plan + canary_echo 全部 `leak failed`。

手工验证：`puts low12=0x6a0 + printf low12=0x810` 双指纹 → [libc.rip](https://libc.rip) /
LibcSearcher（镜像已装 1.1.5）→ **`libc6_2.23-0ubuntu11.3_amd64`**（Ubuntu 16.04）→
用其 `system=0x453a0` / `binsh=0x18ce57` 偏移打穿远程，`cat /flag` 真取
`CTF2{b884870c-…}`。

这正对应 `PROGRESS.md §4` 早登记的边界「无 libc 的 ret2libc（远程）」：
`--libc` 用户给文件时已支持（`model.Challenge.libc_path`），缺的是**没给 libc 时的自动识别**。

## 2. 目标

1. 新模块 `autopwn/engine/libcsearch.py`：双符号 low12 → 识别 libc → 返回 `system` / `binsh` 偏移；
2. `_try_ret2libc` / `_try_canary_echo` 的「leak failed」路径接入：stage1 多泄一个 GOT，
   识别后按 `base = leak_puts - libc_puts_offset` 重算 → stage2 正常执行；
3. `--libc` 路径完全不变（用户给了就用给的）；本地（容器 2.35）路径完全不变；
4. repeater 远程实例全自动 `=> SHELL` + `--cmd cat /flag` 真取 flag。

## 3. 范围

**做：**

- `libcsearch.py`：
  - `identify(low12_map: dict[str, int]) -> Optional[dict]`：LibcSearcher 双条件识别，
    多候选时取第一个（同 Ubuntu 系列关键符号一致）；返回 `{"id", "system", "binsh", "puts", ...}` 偏移
  - LibcSearcher 不可用/无候选 → 可选 HTTP 回退 `libc.rip /api/find`（超时 10s，失败静默 None）
- `orchestrator.py`：
  - `_try_ret2libc` / `_try_canary_echo` 在 `_find_libc_base` 失败且是**远程**时，
    用已泄漏的 puts 值 + 第二符号（printf@got）做识别（需 stage1 的 ROP 多泄一个 GOT）
  - `strategies.s_ret2libc` / `s_canary_echo` 的 stage1 ROP 改为「泄两个 GOT」——仅远程无 libc 时
- `bench/RESULTS.md` 登记向量

**不做：**

- 不下载远程 libc 文件落盘（只取符号偏移，够 stage2 用）
- 不改本地判定路径；不动 `--libc`；不做 libc 文件校验（md5 对拍属后续）
- 不给 32 位 / 静态题做识别（low12 指纹库覆盖 amd64 动态）

## 4. 设计要点

| 项 | 约定 |
|---|---|
| 指纹 | `low12(sym_addr) & 0xFFF`，双符号（puts + printf）足够唯一定位到 Ubuntu 系 1~2 个候选 |
| 候选歧义 | 2.23 的 11.2/11.3 关键符号一致 → 取第一个不影响 stage2；候选数 >1 时 notes 记录 |
| base 重算 | `base = leak_puts - cand["puts"]`，校验 `base % 0x1000 == 0` 且落在 `0x7f..` 段，否则放弃 |
| 第二泄漏 | stage1 ROP 尾部再挂 `pop_rdi(printf@got); puts@plt`——puts 输出两行，按行解析 |
| 判定安全 | 识别失败 → 原样返回 `leak failed`，不放宽判据 |
| LibcSearcher 交互坑 | 多候选 `determine_the_libc()` 会 `input()`——模块内用 monkeypatch stdin / 直接查 `libc_list` |

## 5. 风险

| 风险 | 缓解 |
|---|---|
| puts 输出两行混淆 `_find_libc_base` | 先按 `stupid!!!` 行解析 puts；第二行按换行切 |
| 远程 puts 全缓冲吞泄漏 | 保留现有 `final_sleep/final_read` 窗口；repeater 实测可收到 |
| LibcSearcher 离线库无候选 | 回退 libc.rip；再失败 → 如实 FAILED（不放宽） |
| 改 stage1 ROP 影响 ch13 / bench_extra | 仅远程无 `ch.libc_path` 时才双泄；本地路径单泄不变；三套回归守门 |

## 7. 实施记录

| 项 | 结果 |
|---|---|
| 新模块 | `autopwn/engine/libcsearch.py`（~130 行）：`candidates()` / `identify()` / `rebase()`；LibcSearcher 离线优先、libc.rip 兜底；符号偏移按字符串 parse（LibcSearcher 的 symbols 值是 hex 字符串，int() 会炸——实测踩过） |
| 双泄 | `s_ret2libc` 远程无 libc 时 stage1 双泄 puts+printf，desc 带 `+printf`；跳过 scanf preset（repeater 的 cont 被喂 1024 → 程序直接退出，三阶段时序全毁） |
| 循环闸 | `_try_ret2libc` 只对 `+printf` plan 喂退出 `9\n`——ch13 的 fgets 循环没有闸，多喂一行把 stage2 顶掉一位（本地 1 attempts → 全败，实测回归后修复） |
| 候选轮换 | `_try_canary_echo`：单符号 puts low12=0x6a0 在 LibcSearcher 有 4 个 amd64 候选（2.18/2.23/2.32/2.38），页对齐区分不了；一个候选打错地址进程就死 → 一连接试一候选，`cand_idx` 跨 attempt 轮换，第 2 个候选（2.23）命中 |
| 远程证据 | `=> SHELL canary_echo … remote-libc[libc6_2.23-0ubuntu11.3_amd64]`（6 attempts，16s）+ `cat /flag` → `CTF2{b884870c-f5f2-4379-9c1d-fb8d7f6b54e8}`，2/2 |
| 本地回归 | ch13 / bench_extra/ret2libc 恢复 1 attempts；repeater 本地 3/3；bench 13/15、bench_extra 5+1、bench_sys 4/4；向量 15/15 |
| 遗留 | 双泄 plan 的 plan 数 5（单 preset）覆盖的 offset 少于本地 40 个——远程失败时可放宽回 preset 变体；libc.rip 兜底路径未实网验证（容器网络可达，留待真实比赛场景） |
