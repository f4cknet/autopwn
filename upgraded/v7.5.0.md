# v7.5.0 — holdout 评测与反过拟合门禁

> 状态：🔄 进行中（holdout 集已建立并完成首轮盲测；门禁脚本待做）
> 触发：`bench` 13/15 被当作验收指标，但 `bench` 就是开发集——**这是「0/10」在流程层的第一因**

## 背景

现有验收只有 `bench / bench_extra / bench_sys` 三套，全部参与过开发。用它们在验收，
等价于用训练集测泛化率。10 道新题 0/10 就是这套指标的盲区。

`PROGRESS.md §3` 的能力矩阵以「代表题目（ch01/ch03…）」为列，是过拟合的可视化证据。

## 目标

1. 建立 holdout 集：题目**只跑不改**，严禁为其改任何策略或事实提取逻辑。
2. 指标从「shell/flag 成功率」改为三个：打通率 / **诊断准确率** / **盲试占比**。
3. 门禁拦住「为单题写死」。

## 范围

1. `holdout/` 目录：**来源改为平台新题（BUUCTF 等），不再用 `chellenges/`**。
   2026-11-14 实测：`chellenges/` 33 项中 31 项已被 `prepare()` 过、30 个有 `results/*.json`，
   池子已耗尽的题测不出泛化。目录约定、铁规与跑法见 [`holdout/README.md`](../holdout/README.md)。
2. `scripts/audit/check_generalization.py`：跑 holdout，输出三指标
   - 打通率 = 解出 / 总数
   - 诊断准确率 = 题型与关键原语判对 / 总数（需人工标注基线）
   - 盲试占比 = `--allow-brute` 产生的 attempts / 总 attempts（**应趋近 0**）
3. `check_hygiene.py` 增规则：diff 中出现硬编码地址 / 偏移（如 `0x400889`、`0x80486f3`）、
   或 `ch.name ==` / 分支里出现题名 → 拒绝提交
4. `PROGRESS.md §3` 改造：「代表题目」列改为「输入形态 × 原语」列

## 不做什么

- 不为 holdout 里的题写任何策略（写了就等于取消 holdout 资格，换新题补入）
- 不追求 holdout 通过率——它是测量工具，不是 KPI

## 风险

| 风险 | 缓解 |
|---|---|
| holdout 泄漏进上下文（我读过后记在心里） | 规则要求：每次为 holdout 改代码前，先把该题的答案从会话里排除；做不到就换题 |
| 诊断准确率需要人工标注，成本高 | 先只标 10 题，后续按新增题累加 |
| 门禁误伤合法硬编码（如固定的 `_start` 偏移） | 白名单：`_entry_sub` / `ptrsize` 等通用常量 |

## 验收

1. `check_generalization.py` 可跑出三指标并写入 `results/holdout.json`
2. `check_hygiene.py` 能拦住一次人为构造的「按题名特判」提交
3. `PROGRESS.md §2` 增加 holdout 一行，且基线表注明「非验收指标」

## 首轮盲测记录（2026-11-14 21:30，v7.4.0 之后，v7.4.1 之前）

> **本节刻意脱敏**：只写类别与计数，不写题名 / md5 / 二进制路径 / 可辨识的唯一字符串。
> 原因见 `holdout/README.md` 铁规 1——执行方读得到本文件，写进去就等于泄漏样本。
> **含题名的完整证据在仓库外**（`D:\hacktools\_holdout_runs\`），由验证方持有。

### 1. 样本准备

- 入池 10 题（平台未做过题目），**剔除 1 题**：与 `bench/` 某题 **md5 完全相同**，不属干净样本
- 2 题附件的 libc / ld 文件名是哈希，`_normalize_dir` 按「名字含 libc」识别会**把 2MB 的 libc 当成题目 bin**；
  已按 `e_type`（2=EXEC 题目 / 3=DYN 库）重整为 `bin` + `libc/libc.so.6` + `libc/ld.so`
  → **这是样本准备层的缺陷，需在 `holdout/README.md` 补一条自动识别规则**
- 实跑 **9 题**；其中 **7 题附件不带 libc**

### 2. 结果

| 指标 | 值 |
|---|---|
| 打通率 | **2 / 9**（两题均 **1 次**尝试即 SHELL） |
| 盲试占比 | **0**（`--allow-brute` 未开；3 题 0 次尝试且报 `UNRESOLVED`） |
| 诊断准确率 | 7/9 归因可信；**2 题误诊**（见下） |

### 3. 归因分类（无题名）

| 类别 | 题数 | 性质 |
|---|---|---|
| 打通（amd64 `ret2libc` / i386 `ret2libc_write` 各一） | 2 | — |
| 数字菜单未导航（tail 停在编号菜单） | 1 | **能力缺口** |
| 全局写 + win，无对应策略 | 1 | **能力缺口** |
| 静态二进制（`static=True`） | 1 | **误诊 + 能力缺口** |
| 未识别到可达溢出（限额 < 偏移） | 1 | 待复核 |
| 交互时序（多轮 prompt） | 2 | 待复核（交 `v7.4.1`） |
| 附件 libc 与二进制不匹配 | 1 | **样本问题，不计引擎** |

### 4. 两处误诊（可复现，需修）

1. **静态二进制被报成「PLT 桩形态未识别」**：`static=True` 的题目本来没有 PLT，
   该文案会把人引向 PLT 解析，而真实缺口是 static ROP。`_audit_facts` 应先判 `ch.prot.static`。
2. **`win` 分类 `endswith("sh")` 过宽**：一个非 shell 路径的垃圾串（结尾是 `sh`）
   被判成 `shell` win，策略随即往假地址跳。应收紧为「`/bin/sh` 精确匹配 或 路径分量末尾是 `sh`」。
