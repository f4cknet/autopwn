## 1. 背景

`autopwn -l Challenge/canary` 在 detect 阶段会先跑 `leakage_canary_value()`，再进入 `canary_fuzz()` 的多重枚举。用户手工观测到终端持续刷 `Starting local process` / `stopped with exit code -6 (SIGABRT)`；根因不是单次卡死，而是本地单进程 canary 爆破路径缺少运行时 stop-loss。

## 2. 目标

让 canary 题在默认配置下变成“有界失败”：超出预算后明确中断、记录原因，并回落到普通失败路径，而不是把整次离线 run 拖成超长任务。

## 3. 范围与非目标

**范围**：`autopwn/cli.py`、`autopwn/context.py`、`autopwn/orchestrator/detect.py`、`autopwn/detect/canary.py`、必要的单元/集成测试，以及 README / 索引同步。

**非目标**：
- 不做 challenge-name 特判
- 不把本任务偷扩成“提高 canary 成功率”
- 不改变既有 candidate/fallback 路径，只在 detect 层加预算阈值

## 4. 实施方向

1. 在 CLI/Context 暴露 canary detect budget（至少包含 wall-time 阈值，允许用户覆盖默认值）
2. `canary_fuzz()` 在预算耗尽时 fail-closed，打印明确日志并返回 `None`
3. detect phase 只把它视为“canary 未拿到”，后续逻辑继续按现有 candidate/fallback 走
4. 默认值要足够保守，既避免 `Challenge/canary` 长时间刷屏，也不影响 `fmtstr1` 这类“canary + fmtstr”题继续走 format-string 路径

## 5. 6 关验收

1. 代码提交并 push 到 `main`

## 7. 风险

- 默认 budget 过小会把未来真正可解的 canary binary 过早 fail-closed，因此必须允许 CLI 覆盖（如 `0=unbounded`）
- 只加 time budget、不加算法优化，意味着 `canary` 仍是 PARTIAL；这是预期，不属于 regression
- integration 中 canary 的退出路径可能从“外层 timeout”变成“内层 fail-fast 返回”，测试应锁定“仍未成功且不会 hang”，而不是绑死某一种退出方式
