# v7.6.0 — 多 agent 无人值守迭代框架

> 状态：🔄 进行中（脚手架已落地，未在服务器实跑）
> 起因：Owner 提出「我只给题库 + 通过率目标，剩下自己迭代」，且不想依赖 GitHub

## 背景

前几轮的协作方式是**人工转述**：评审方写长文 → Owner 贴给实施方 → 实施方回执 → 再转回。
两个 Agent 还共用同一个工作树，靠人工挑文件提交才不互相覆盖。这套流程有三个结构问题：

1. **交接成本高**：每轮一段长指令，且容易漏（实施方会按仓库默认流程"补全"动作）。
2. **工作树冲突**：同一目录、同一 `main`，一方的未提交改动会出现在另一方 `git status` 里。
3. **判定靠自述**：「通过」由 Agent 自己说，容易出现「策略跑完没报错 = 成功」。

## 目标

把「谁说了算」从 Agent 手里拿走：

```
分数 → 冻结评测器（脚本，Agent 只读）
裁决 → supervisor（纯 Python，无 LLM）
归因 → Agent（唯一由 LLM 承担的部分）
例外 → Owner
```

## 范围

`scripts/agent/`：

| 文件 | 职责 | 关键约束 |
|---|---|---|
| `run_eval.py` | 跑 dev + 三套回归 → `state/last.json` | 不传 `--allow-brute`；只出数字，不做判断 |
| `supervisor.py` | 一轮驱动与裁决：impl → 评测 → 四道锁 → merge/revert | **不调用任何 LLM**；判据哈希每轮校验 |
| `prompt_impl.md` | 实施方 prompt | 只写「不许」；禁止自评通过 |
| `prompt_verify.md` | 验证方 prompt | 禁止出现数字；只做失败分类与误诊指认 |
| `deploy.sh` | 服务器初始化：用户 / 权限 / bare origin / 冻结评测器 | 自带 `[OK]/[FAIL]` 权限自检 |
| `README.md` | 傻瓜式部署指南 | 含题库三个坑与常见故障 |

### 四道锁（`supervisor.guarantees_ok`）

1. **判据锁**：`oracle.py` sha256 每轮比对，变了 abort
2. **回归锁**：`bench 13 / bench_extra 6+1 / bench_sys 4` 掉了即 revert
3. **盲试锁**：`brute_attempts != 0` 即 revert
4. **样本锁**：`sealed/` 由 root 持有 `chmod 700`，两个 Agent 均不可读

## 不做什么

- 不做 GitHub Actions / PR 流程（owner 明确不用）
- 不做「Agent 自由对话」：上下文通过 `state/*.json` 传递，不通过聊天
- 不自动改判据（`oracle.py` 口径、`FLAG_RE`、gate 是否算成功）——这四条永远需要人批

## 风险

| 风险 | 缓解 |
|---|---|
| Agent 改评测器 | 执行版在 `/srv/autopwn/eval/`（root 755），仓库里的副本改了也不生效 + sha 校验 |
| 无人值守烧 token | `--rounds` / `--max-hours` / `--max-turns` 三重上限；连续 2 轮无提升即停 |
| 停在半夜没人知道 | `state/ALERT`；建议接 webhook 推送（未实现） |
| 3 轮不涨还在跑 | 停止条件 + 文档明写「3 轮不涨 = 缺能力，需要人加策略」 |
| 样本准备错（重复 / 缺 libc / 带 flag） | README §4 三坑清单 + 逐题 `--facts-only` 自检 |

## 验收

1. `supervisor.py --rounds 0` 能完成基线评测并写出 `state/best.json`
2. 人为改 `oracle.py` → 下一轮 `why=判据被改` 并停
3. 人为让某轮 `bench` 掉一题 → 该轮 commit 被 `reset --hard` 回滚
4. `deploy.sh` 三行权限自检全 `[OK]`
5. 服务器上跑通 3 轮，`history.jsonl` 有 3 行

> 本轮只交付脚手架；**服务器实跑与真实曲线属于 v7.6.1**。
