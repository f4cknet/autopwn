## 1. 背景 / 归类理由

`Challenge/canary` 暴露的不是“某一道题没有打通”，而是一个可复用的链路缺口：

1. detect 阶段把 **具体 canary 值** 写进 `ctx.canary`，但后续 strategy 会新起进程；本地单进程题里，新旧进程的 canary 不可复用
2. 现有 canary strategy 默认假设“泄露”和“溢出”发生在同一次输入或不同进程，不覆盖 **同一会话先 fmt leak、再第二输入 BOF** 的题型
3. 现有验证默认看 `echo PWNED`，但本任务要以 **真实执行 `whoami` 成功** 作为 shell 成功判定

如果继续针对 `Challenge/canary` 单题补丁，会再次把 challenge 特征写进 strategy；因此本次按“same-session canary 泄露计划 + 通用 x32 两阶段 ret2libc”立项。

## 2. 目标

在**不写 challenge-name 特判**的前提下，为“本地 / x32 / fmtstr 后仍有第二输入点 / 栈 canary 开启”的题型增加通用链路：

- detect 侧识别并缓存 **可重放的 canary 泄露计划**
- strategy 侧在**同一进程**中完成 `fmt leak -> canary-aware ret2libc puts -> 回到 main -> 第二轮 ret2libc system("/bin/sh")`
- 仅当 `whoami` 返回有效用户名时，才认定 shell 成功

## 3. 范围与非目标

**范围**：

- `autopwn/context.py`
- `autopwn/detect/*`
- `autopwn/exp/registry.py`
- `autopwn/exp/strategies/*`
- `autopwn/core/shell_verify.py`
- 相关 unit / integration / Challenge 手工验证
- `upgraded.md` / `upgraded/v4.1.22.md` / `refactor.md`

**非目标**：

- 不写 challenge-name / symbol-name 特判
- 不顺手把全部 strategy 的默认验证协议从 `PWNED` 全量切到 `whoami`
- 不在本任务里扩到 remote / x64 same-session canary

## 4. 实施方向

1. 在 `ExploitContext` 中新增 `CanaryLeakPlan` 抽象，表达“如何在同一会话里再次拿到本进程 canary”，而不是缓存一次性的旧 canary 值
2. detect 层为“fmtstr + second input sink + local canary”题型尝试生成 same-session 泄露计划：
   - 顺序 `%x` 泄露 payload
   - 基于本进程第二输入点的 crash-signal 探针定位 canary 栈索引
   - 静态推导 `buffer_to_canary` 与 `post_canary_padding`
3. 在现有 `canary-ret2libc-put-x32` 本地 strategy 中增加 same-session 分支，在同一 `process()` 中执行：
   - 第一轮：泄露本进程 canary
   - 第二轮：canary-aware stage1 `puts(puts@got)` 泄露 libc
   - 回到 `main`
   - 第三轮：重新走首个输入点后，发送 canary-aware stage2 `system("/bin/sh")`
   - 用 `whoami` 验证 shell
4. `ret2libc-put` 的 canary 变体去掉对 `has_system` 的过严前置 gate，避免在“二进制没导入 system，但 libc 可解出 system”时被提前过滤
