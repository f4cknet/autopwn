# v7.4.0 — 守卫分析与约束求解（逻辑校验题通道）

> 状态：✅ 已完成（2026-11-14；按评审拆 a/b/c 三次提交，回执与实施记录见文末）
> 触发：10 题里有 4 道 win 被「条件分支」守着，现有策略完全无视守卫，一律按 ret2win 打

## 实施设计（v7.4.0）

1. `guard.py` 修正：
   - jcc 助记符进入求解器；`jne/jnz` 的 `want_ne = must_take`，
     `je/jz` 的 `want_ne = not must_take`（492f 的 `je fail` 必须落下）；
     只支持相等/不等，`ja/jb/jg/jl` 记 `unknown`。
   - 求解器直接返回 `(conds, ones, length, status, reason)`；删除
     `pred/pair/len` 打包。`or == 0` 拆两条等式，`(x|y) != 0` 记 `oneOf`，
     `xor` 归一，`ret` 递归判定函数返回常量块（深度 1）。
   - 只收 sink 之后、且 taken/fallthrough 恰好一条能到 win 的条件；PIC ebx
     仅在函数内出现 `call __x86.get_pc_thunk.bx` 时启用；`_GLOBAL_OFFSET_TABLE_`
     缺失 → `unsupported`。
   - 载荷构造避免把 NUL 塞进 `%s`：4ee0 只写 `A*0x34 + \x11`，`var+0x38`
     的零值由 `.bss` 保证；492f 产出 121 字节 `dead-…-beef`。
   - fmt 全局门解析 `mov [esp], reg/imm`（71b6），选第一个与 sink 缓冲相同的
     `printf`；探针序号、`fmtstr_payload`、80 字节窗口由策略层负责。
   - 新增 `Backfill` + `find_backfills`：434c 的 `strncmp(input, 参数, 4)`
     且参数串在调用者被打印 → 回填前 4 字符；只产出 gate 证据，不算 shell。
2. 接入：`Facts.guards/backfills`、`Plan.meta`、`s_guard_write` /
   `s_guard_fmt` / `s_guard_backfill`、orchestrator 的 `guard:*` 分派与
   `_try_guard_backfill`、oracle 的 `judge_gate`/`judge_win_executed`、
   CLI `--facts-only` 输出。
3. 判据不变：`judge_gate`/`judge_win_executed` 固定 `ok=False`；gate 通过
   只写 `cause="gate_passed"` 证据，不增加 shell/flag 计数。

## 背景

| 题 | 守卫形式 | 现有引擎 |
|---|---|---|
| 三 492f | `strlen(buf)==121` + `buf[0..4]=="dead-"` + `buf[0x74..0x78]=="-beef"` | 不识，盲打 70 次 |
| 一 4ee0 | `or [buf+0x34], [buf+0x38]` 非零才进成功分支 | 不识（且 PLT 都没解析出来） |
| 七 71b6 | `cmp [全局], 4` 后 `system("/bin/sh")` | 不识，靠 fmt 写全局本来可解 |
| 六 434c | `srand(time)` 生成串→打印→`strncmp` 比对 | 不识，当 ret2libc 打 40 次 |

这四题的本质都是**让程序自己的判定通过**，不是劫持控制流。缺这一层，这类型题永远 0。

## 目标

新增 `autopwn/engine/guard.py`：在生成任何计划之前，先回答「到 win 的路径上有什么条件，这些条件能不能由输入满足」。

## 范围

1. `guard.py`：从 win 入口反推路径上的条件分支，抽取
   - `cmp byte [buf+i], imm` 序列 → `const_seq`（可直接构造输入）
   - `strlen(buf) == N` → 长度约束
   - `strncmp(input, X, n)` → 若 X 来自 `rand/read`（不可控）→ `uncontrolled`
   - 无分支 → `none`
2. 分类后的动作：
   - `const_seq` / 长度约束 → 直接生成输入（题三、题一、题七）
   - `uncontrolled` 且该串被 `printf/puts` 打印过 → 「回填」策略：先读走打印的串再喂回去（题六）
   - `uncontrolled` 且未打印 → 判定为能力边界，登记进 `PROGRESS §4`
   - `none` → 不进本通道，走既有策略
3. `oracle.py` 新增 `win_executed` 态：win 真的跑了但没 flag 内容（题五的 `system("echo flag")`）
4. `Plan` 新增 `tag="guard:…"`，orchestrator 分派
5. **bss-gate-write 策略**：题一的解法是「`scanf %s` 无限写 bss + 把门控值改成 0x11 → 进 `system` 分支」。
   守卫求解出「门控在 `buf+0x34/0x38`」只是拿到答案，还需要一条策略把它变成实际负载：
   从「写入起点 + 门控偏移」算出 payload 长度与内容 → 单次 `Send`。缺这一环，Step 3 只解一半。

> Owner 2026-11-14 手工实证：题一的门控值 0x11 写的是 bss 内相邻全局，不是栈帧；
> 因此 `v7.3.1-a`（PLT 修复）与本节守卫求解都到位后，仍需本条策略才可能打通。

## 不做什么

- 不做符号执行 / z3（先做常量比较和字符串约束，覆盖 3/4 题）
- 不做堆题、不做 SROP

## 风险

| 风险 | 缓解 |
|---|---|
| 抽取到「数据流无关」的 cmp，生成错误输入 | 只接受「比较目标可追溯到输入缓冲」的序列，其余记 `unknowns` |
| 回填策略依赖时序，容易 flaky | 同一进程内读-写，失败原因单列，不计入策略成功率 |
| 范围蔓延成「通用逆向」 | 硬边界：只支持 `cmp/test/strlen/strncmp` 四种 |

## 验收

1. 题三：送入 `"dead-" + 111 字符 + "-beef"` 后 main 走 `system("/bin/sh")`，**真拿 shell**
2. 题一：覆盖 `buf+0x34/0x38` 后进成功分支（需 `v7.3.1-a` 先修 PLT）
3. 题六：回填打印的随机串后通过 `mem_test`
4. bench 基线不掉；`unknowns` 里 `guard` 条目带具体不可满足原因

### A. 会直接导致验收失败的（P0，开工前改）

**A0（新增，最高优先）. `guard.py` 把「虚拟地址」当「指令下标」用，实参解析层整体失效。**

`find_guards()` 在题三 / 题一 / 题七 上实测返回 **0 条守卫**（三题全部）。
根因不在算法方向，而在下标空间混用：

```python
# guard.py:616（以及 668 / 678 / 711 / 721 / 745 / 755 / 779，共 8 处同型）
for k in range(idx - 1, max(lo - 1, idx - 16), -1):
```

- `idx` 是 `d.insns` 的**下标**（题三 `call system` @0x4008dc → idx=149）；
- `lo` 传进来的是**函数入口虚拟地址**（`entry = 0x400889`）；
- `max(0x400889 - 1, 149 - 16)` = **4196488** ⇒ `range(148, 4196488, -1)` 是空循环 ⇒ 恒返回 `None`。

实证（容器内直接调）：

```
call@ 0x4008dc entry=0x400889
  _arg_text  -> None          ← 应为 ("/bin/sh", 0x4009a7)
  _sink_buf  -> None
read_cstr(0x4009a7) = '/bin/sh'   ← 字符串本身没问题
_norm_reg('edi')   = 'rdi'        ← 寄存器归一也没问题
_resolve_reg(rdi)  = None         ← 断在这里
```

受影响函数（全部同一个 `max(lo - 1, …)` 写法）：
`_resolve_reg` / `_sink_buf` / `_push_expr` / `_pushes_before` / `_last_push_expr` /
`_buf_from` / `_read_count` / `_arg_text`。

修法（二选一，建议后者）：
```python
# 1) 调用方统一换算成下标
lo_i = d.by_addr.get(entry, 0)
# 2) 或每个函数开头归一（改动面小、不依赖调用方）
lo_i = d.by_addr.get(lo, 0) if lo > len(d.insns) else lo
...
for k in range(idx - 1, max(lo_i, idx - 16), -1):
```

验收：`find_guards()` 在三题上至少各返回 1 条 `Guard`；
题三的 `_arg_text` 能解析出 `("/bin/sh", 0x4009a7)`。

> 这一条优先级高于 A1/A2/A3：A1/A2 讨论的是「分析方向对不对」，
> A0 是「根本没跑起来」。不修 A0，A1/A2 的修正无法验证。

**A1. 题三的守卫不在 sink 之后，在 callee 里 —— 按线性扫描会收到 0 个条件。**

你写的是「只收 sink 之后、且 taken/fallthrough 恰好一条能到 win 的条件」。
但题三的 `cmp` 全在 `Serialization`（`0x4007f9` 起），`scanf` 在 `main`（`0x4008b5`），
中间隔着 `0x4008bf: call 4007f9 <Serialization>`。

- 线性扫描 ⇒ 题三 0 条件 ⇒ 验收项 1 不可能达成。
- 要求：从 win 反推时**必须跟随 call 边（至少深度 1）**；
  并且 `0x4008c4: test eax,eax` / `0x4008c6: je 4008eb(fail)` 这种**用返回值当判据**的也要纳入
  （你写的「`ret` 递归判常量块（深度 1）」是另一件事，不能替代这条）。

**A2. 题一是两级守卫，不是一级 —— 只解第一级会永远得不到 0x11。**

```
12eb: or   eax,edx        ; 第一级：(buf[0x34] | buf[0x38]) != 0 才跳 131e
12ef: jne  131e
...
132a: xor  eax,0x11       ; 第二级：(buf[0x34] ^ 0x11) | buf[0x38] == 0 才落到 system
132d: or   eax,edx
1331: jne  1347
133d: call system         ; 参数 [ebx-0x1fc3]，实测 e.string(0x203d) == b"/bin/sh"
```

你写的「`(x|y) != 0` 记 `oneOf`」对**第一级**成立，但只解到这里，求解器会输出「任意非零」，
写不出 0x11。
要求：**以「落到 win 的最后一级」为准**，前面各级只做一致性校验，不单独产出约束。

（顺带确认你的载荷结论是对的：`buf[0x34]` 必须**恰好** 0x11，`buf[0x38]` 必须为 0；
只写 `A*0x34 + \x11`、靠 `.bss` 零值补齐，完全正确——我原稿把它当成「任一非零」，你更准。）

**A3. `judge_gate` 固定 `ok=False` 会把真 shell 记成证据。**

题一 / 题三 / 题七 的 gate 通过后**紧跟 `system("/bin/sh")`**（题一 `0x133d`、题三 `0x4008dc`、
题七 `0x80485e6`），这是真 shell，不是「gate 证据」。

如果策略在 gate 通过后就返回 `gate_passed, ok=False`，等于又做了一次
「打通了但账上不算」。要求改成：

```
gate 通过 → 继续 judge_shell（发 id / echo PWNED_42）
  有 uid=/marker → 记 SHELL（正常计数）
  无 shell 输出   → 才落 gate_passed（ok=False，仅证据）
```

另外：`win_executed`（题五）现在**触发不了**。v7.3.1 已把 `system("echo flag")` 降级成
`Win.kind="decoy"`，而 `s_ret2win_flag` 只认 `kind == "flag"` ⇒ 根本不会生成计划。
要有这条证据，得显式允许对 decoy 打 1 次并计入「已尝试、不可得分」。这一环你还没接。
